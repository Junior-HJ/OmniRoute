- **fix(providers):** align the `codebuddy-intl` executor with the official CodeBuddy International CLI (`CLI/2.175.0`) instead of the IDE profile it had drifted into, so identity headers, the request body, the model catalog, telemetry and rate-limit handling all describe the same request: the `X-Conversation-*` / `X-Root-Request-ID` / `X-Trace-ID` identifier families are modelled separately and kept correlated per request (a `WeakMap` on the request body replaces an instance field that leaked ids between concurrent turns on the cached executor singleton); `GET /v3/config?repos[]=` becomes the authoritative model catalog, fetched at runtime, cached per account with a TTL and merged into a curated list that is now aligned with it, with a fetch failure never emptying the model picker; synthetic report events and OTLP spans are built from the real execution and actually sent to `/v2/report` and `/v1/traces` as a non-blocking side channel (`OMNIROUTE_CODEBUDDY_TELEMETRY=0` opts out); and a `429` carrying an unlock date now reaches the shared cooldown through its `{code, msg, data:{resetTime}}` envelope, so the account is frozen until that date instead of being retried after generic backoff. A live run against `www.codebuddy.ai` with a real account turned two of those assumptions into evidence and exposed one defect: `/v1/traces` accepts the OTLP/HTTP JSON encoding (HTTP 200), while `/v2/report` rejected the batch with `10001:eventCode is empty or not string` because it validates `eventCode`, `reportDelay` and a numeric `timestamp` at the top level of the envelope, not inside `events[]` — the batch now carries them, and both endpoints answer 200. The same run showed the curated lineup had drifted from `/v3/config` (`gemini-3.5-flash`, `minimax-m3` and `step-5-preview` are no longer served), so they are dropped ([#18098](https://github.com/cheaper-inference/OmniRoute/pull/18098)).
